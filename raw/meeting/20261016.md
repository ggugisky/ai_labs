## Overview

ggugi님이 여러 AI 코딩 에이전트를 하나의 인터페이스로 연결하는 하네스/게이트웨이 구조와 Margaret Gateway를 소개했다. 핵심 문제는 Codex·Claude Code·OpenCode·Copilot처럼 서로 다른 에이전트의 인터페이스와 세션이 분리되어 컨텍스트가 끊기는 것이며, Margaret은 공통 REST+SSE API와 세션 계층으로 이를 통합하는 접근이다.

## Discussion

### 1. 문제 정의

- AI 코딩 도구마다 별도 CLI와 대화 컨텍스트를 사용해 도구를 바꿀 때 맥락이 끊긴다.
- 클라이언트마다 각 도구의 연동 방식을 따로 구현해야 하므로 모바일·Slack·웹 접근성을 확장하기 어렵다.
- 클라이언트는 개별 에이전트를 알지 않고 공통 프로토콜만 사용하도록 추상화할 필요가 있다.

### 2. Margaret Gateway의 핵심 구조

- 하나의 REST+SSE API 뒤에 Codex, OpenCode, Claude Code, Copilot 등의 백엔드를 연결한다.
- 에이전트별 어댑터는 SDK 우선, SDK가 불안정하거나 없으면 headless CLI, 마지막 수단으로 interactive CLI/PTY를 사용하는 계층형 전략을 취한다.
- 각 Gateway 세션은 하나의 native CLI 세션에 바인딩되어 대화 연속성을 보존한다.
- 세션 생성 시 `agent_id`, `model_id`, `client`, `title`을 명시하며, 생성 뒤 에이전트·모델·워크스페이스는 고정한다.

### 3. 클라이언트와 연동

- 음성 앱, Slack DM, 웹 UI, 로컬 CLI가 같은 세션을 공유할 수 있다.
- Slack Socket Mode를 Gateway 내부에 포함할 수 있어 별도 중계 서버 없이 Slack에서 에이전트를 호출하는 구조를 제시했다.
- 음성 클라이언트는 WebSocket으로 텍스트 스트림을 받고, 응답 완료 이벤트와 Markdown 문서 링크를 전달받는다.

### 4. 운영·확장 관점

- FastAPI + SQLite 중심의 작은 스택으로 self-hosting을 목표로 한다.
- 선택적으로 Bearer token 인증을 적용할 수 있다.
- LightRAG 기반 semantic memory를 에이전트 컨텍스트에 주입하는 확장점이 있다.
- 백엔드별 모델 목록과 capabilities를 `/agents`에서 조회해 클라이언트가 지원 모델을 동적으로 선택할 수 있다.

## Decisions

- [x] AI Labs에서 하네스를 단순한 CLI 래퍼가 아니라 에이전트·세션·클라이언트 사이의 공통 프로토콜 계층으로 바라본다.
- [x] 후속 검토는 에이전트 수보다 세션 연속성, 권한 경계, 모델 선택, 관측 가능성을 우선 기준으로 삼는다.
- [ ] 작은 개발 업무를 대상으로 최소 기능 PoC를 먼저 검증한다.

## Summary

이번 미팅의 핵심은 여러 AI 에이전트를 하나의 세션·프로토콜·클라이언트 경험으로 묶는 하네스의 구조적 가치다. Margaret Gateway는 REST+SSE API, native CLI 세션 바인딩, 계층형 어댑터, Slack/음성/웹 연동으로 이 문제를 해결하려는 구현이다. AI Labs에서는 우선 두 개의 에이전트를 연결한 작은 PoC로 세션 연속성과 운영 안전성을 검증하고, 이후 Slack 또는 음성 인터페이스와 semantic memory를 확장 후보로 검토한다.
